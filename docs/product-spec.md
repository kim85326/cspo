## 1. 產品概述

### 1.1 核心問題
「我買的股票到底賺了還是虧了？我花時間選個股，到底值不值得？」

### 1.2 目標使用者（Persona）
台灣的長期散戶：

- 大部分資金**每月定期定額買 ETF**（例如 0050、006208），作為「核心部位」。
- 另外拿一部分資金**自己挑個股**，作為「衛星部位」，有的長抱、有的幾個月就賣。
- 會領股利，在意股利有沒有被算進報酬。
- 不是當沖客，不需要即時報價與每日推播。

### 1.3 產品一句話
**每個月幫你確認：花時間選股，到底值不值得。**

### 1.4 明確不做（全部 Phase 都不做）
- 給出買進／賣出建議（有投顧法規風險）
- 當沖、融資融券、借券、期貨、選擇權
- 即時報價（盤中跳動）
- 真實下單（見 `docs/context-for-ai.md` 第 10 節）

### 1.5 與現有程式的對照（iteration-1 分支）

**已完成、可沿用的部分**

| 現有 | 對應本規格 | 處理方式 |
|---|---|---|
| Story 001 單筆盈虧 | M-04 持股明細 | 計算改為 3.3–3.5 的公式（含手續費、稅、已實現） |
| Story 002 股票選擇器 | M-01 搜尋證券 | 沿用；補上上櫃股票與「個股／ETF」類型標籤 |
| Story 003 多檔比較 | M-04、M-05 | 由「持股明細」與「首頁總覽」取代，不再限制最多 5 檔 |
| Story 004 記住持股 | M-07 本機儲存 | 沿用 AsyncStorage；資料結構改為交易紀錄（見下方「資料搬移」） |
| Story 005 截圖匯入 | P2-06 拍照匯入 | 沿用辨識與核對流程；核對完成後改為建立買入交易 |
| Google 登入（開發中） | P2-01a | 沿用；維持功能開關 |
| 證交所真實行情 | 第 5 章 | 沿用；MVP 補上櫃 |

**最大的改變：從「持股快照」改成「交易紀錄」**

現在一筆 `Holding` 是「代號 + 買入價 + 數量」，代表一次買入。本規格改成記錄每一筆**交易**（買、賣），持股由交易**計算**而來。這樣才能處理分批買入、賣出、已實現損益與股利。`src/domain/types.ts` 的 `Holding` 會變成計算結果，而不是使用者輸入。

**資料搬移**：使用者手機上已存的 `SavedHolding`，在升級後第一次開啟時，每筆轉成一筆買入交易（日期用舊資料的買入日期，沒填或日期無法辨識時才用搬移當天，PO 決策 27-10-2026；手續費依 3.2 計算、備註「由舊版資料轉入」），轉換成功後才刪除舊資料。

**glossary 需要更新的名詞**

| 名詞 | 現行定義 | 本規格定義 |
|---|---|---|
| 買入成本 | 買入價 × 數量 | 改稱「持有成本」，含買入手續費（3.3） |
| 盈虧 | 現值 − 買入成本 | 拆成已實現損益、未實現損益，加上股利成為「總報酬」（3.4、3.5） |
| 現值 | 現價 × 數量 | 改稱「市值」，定義相同 |
| 持股 | 一筆代號 + 買入價 + 數量 | 由交易計算出的持有狀態 |
| 比較 | 多檔依報酬率排名 | 不再是獨立功能，由持股明細的排序取代 |

## 2. 名詞定義

| 名詞 | 定義 |
|---|---|
| 證券（Security） | 一檔可交易的標的，例如 `2330 台積電`、`0050 元大台灣50`。分為「個股」或「ETF」 |
| 交易（Transaction） | 一筆買入或賣出紀錄 |
| 持股（Holding） | 某檔證券目前持有的狀態，**由交易與股利紀錄計算而來，不直接儲存** |
| 核心部位 | 標記為「核心」的持股，預設為所有 ETF |
| 衛星部位 | 標記為「衛星」的持股，預設為所有個股 |
| 持有成本 | 目前持有股數對應的成本，含買入手續費 |
| 平均成本 | 持有成本 ÷ 持有股數 |
| 已實現損益 | 已賣出部分的損益（扣除賣出手續費與證交稅） |
| 未實現損益 | 尚未賣出部分若以現價賣出的預估損益（已扣預估賣出費用） |
| 總報酬 | 已實現損益 ＋ 未實現損益 ＋ 已領現金股利 |
| 累計投入 | 所有買入交易的金額加買入手續費的總和 |
| 參考價 | 用來計算市值的價格，為最近一個交易日的收盤價 |

## 3. 計算引擎（共用規則）

本章是整個 App 的正確性核心。**所有畫面上的數字都必須來自這裡定義的公式。**

### 3.1 數值精度
- 內部計算保留完整精度（不可中途四捨五入），只在**顯示時**四捨五入。
- 金額顯示到整數元，加千分位，例如 `152,880`。
- 平均成本、股價顯示到小數點後 2 位。
- 百分比顯示到小數點後 2 位，例如 `13.88%`。
- 正數顯示紅色、負數顯示綠色（台灣股市慣例），並加上 `+`／`-` 號。
- 金額請避免使用浮點數累加誤差；建議使用 decimal 函式庫或以「分」為單位的整數運算。

### 3.2 交易成本規則

**手續費**
```
手續費 = max( floor(成交金額 × 手續費率 × 手續費折扣), 最低手續費 )
成交金額 = 成交價 × 股數
```
- `手續費率` 預設 `0.001425`
- `手續費折扣` 預設 `1.0`（無折扣），使用者可在設定修改，例如 `0.28` 代表 2.8 折
- `最低手續費`：股數 ≥ 1000 預設 `20` 元；股數 < 1000（零股）預設 `1` 元。兩者皆可在設定修改

**證交稅**（只有賣出才收）
```
證交稅 = floor(成交金額 × 證交稅率)
```
- 個股：`0.003`
- ETF：`0.001`
- 證交稅率存在證券資料上，使用者可在單筆交易覆寫（例如債券 ETF 免稅）

**使用者覆寫**：每筆交易的手續費、證交稅都由系統自動帶入，但使用者可以手動改成券商對帳單上的實際數字。覆寫後以使用者輸入為準。

### 3.3 平均成本法（移動加權平均）
同一檔證券，依交易日期排序後逐筆處理（同一天依建立時間排序）：

- **買入**：`持有股數 += 股數`；`持有成本 += 成交金額 + 手續費`
- **賣出**：
  - `賣出淨額 = 成交金額 − 手續費 − 證交稅`
  - `賣出成本 = 平均成本 × 賣出股數`
  - `已實現損益 += 賣出淨額 − 賣出成本`
  - `持有股數 −= 賣出股數`；`持有成本 −= 賣出成本`
  - 賣出**不改變**平均成本
- **股票股利（配股）**：`持有股數 += 配股股數`，持有成本不變（因此平均成本下降）
- 持有股數歸零後再買入，平均成本從新的買入重新計算。
- **任何新增、修改、刪除交易或股利，都要從頭重算該證券的所有紀錄。**

### 3.4 未實現損益
```
市值         = 參考價 × 持有股數
預估賣出費用 = 依 3.2 計算以參考價賣出全部持股的手續費 + 證交稅
未實現損益   = 市值 − 預估賣出費用 − 持有成本
```

### 3.5 報酬
```
總報酬       = 已實現損益 + 未實現損益 + 已領現金股利
簡單報酬率   = 總報酬 ÷ 累計投入
```
- 持股層級、核心部位、衛星部位、整體，都用同一套公式，只是加總的範圍不同。
- `累計投入` 為 0 時，報酬率顯示 `—`。

### 3.6 持有天數
從「目前這一段持有」的第一筆買入日期算到今天。若曾經賣光再買，從賣光後的第一筆買入開始算。

### 3.7 驗收用範例（必須寫成單元測試）

設定：手續費率 0.001425、折扣 1.0、最低手續費 20 元。證券：2330（個股，證交稅 0.003）。

| 步驟 | 動作 | 計算 | 結果 |
|---|---|---|---|
| 1 | 買 1000 股 @ 600 | 金額 600,000；手續費 floor(855.0) = 855 | 持有 1000 股，成本 600,855 |
| 2 | 買 1000 股 @ 500 | 金額 500,000；手續費 floor(712.5) = 712 | 持有 2000 股，成本 1,101,567，平均成本 550.7835 |
| 3 | 賣 500 股 @ 650 | 金額 325,000；手續費 463；證交稅 975；淨額 323,562；賣出成本 275,391.75 | 已實現損益 **48,170.25**；剩 1500 股，持有成本 826,175.25，平均成本仍為 550.7835 |
| 4 | 領現金股利 5,000 | — | 已領股利 5,000 |
| 5 | 參考價 620 | 市值 930,000；預估手續費 1,325；預估證交稅 2,790 | 未實現損益 **99,709.75** |
| — | 彙總 | 總報酬 = 48,170.25 + 99,709.75 + 5,000 | 總報酬 **152,880**；累計投入 1,101,567；簡單報酬率 **13.88%** |

零股範例：0050（ETF）買 30 股 @ 150 → 金額 4,500，手續費 max(floor(6.41), 1) = **6**。

錯誤範例：持有 1500 股時輸入賣出 2000 股 → 必須被拒絕，提示「賣出股數超過持有股數（1,500 股）」。

## 5. 市場資料

- 需要三種資料：**證券清單**、**每日收盤價**、**除權息資料** `[P2]`。
- **現況**：`src/data/twseSource.ts` 已接證交所 OpenAPI 的每日收盤行情，只涵蓋**上市**股票與 ETF。
- **MVP 需補**：櫃買中心 OpenAPI 的**上櫃**股票，否則使用者搜尋不到上櫃股（例如部分熱門中小型股）。
- **Phase 2 需補**：歷史收盤價、還原股價與除權息資料。建議評估 FinMind API（同時提供這三種資料）。
- **資料來源必須封裝在 `src/data/` 的介面後面**（比照現有 `PriceSource`、`StockDirectory`），方便日後替換，自動化測試用假來源。
- 每次開啟 App 時，若最新價格不是最近一個交易日的收盤價，就更新一次。不需要盤中更新。
- 畫面上要顯示「價格更新時間」。
- 取得價格失敗時：沿用快取價格並顯示「價格可能不是最新」；完全沒有價格的持股，市值與未實現損益顯示 `—`，並且**不計入**總市值，總覽顯示提示「有 N 檔持股缺少價格」。

## 6. MVP 規格

**MVP 目標**：使用者能記錄交易與股利，看到每檔持股與整體的真實賺賠，並區分 ETF 與個股。資料存在裝置本機，不需要帳號。

### M-01 搜尋證券

### P2-02 定期定額自動記帳
**User story**：我每個月都定期定額買 ETF，不想每個月手動輸入。

規則欄位：證券、每期金額、每月扣款日（1–28）、開始日期、結束日期（選填）、啟用狀態。

產生邏輯：
- 扣款日遇到非交易日，順延到下一個交易日。
- 成交價 = 該交易日收盤價。
- `股數 = floor(每期金額 ÷ (成交價 × (1 + 手續費率 × 手續費折扣)))`，手續費依 3.2（零股最低手續費）。
- 產生的交易 `source = dca`，在列表上有「定期定額」標記，使用者可編輯成券商實際成交的價格與股數。
- App 開啟時，補產生所有「已到期、但尚未產生」的交易（例如一個月沒開 App）。
- 該交易日收盤價還沒有資料時，先不產生，下次開啟再補。
- 同一規則同一期只能產生一筆（以規則 ID + 年月去重）；使用者刪除自動產生的交易後，**不可**再自動補回。

範例：每期 5,000 元買 0050，成交價 180 → 股數 floor(5000 ÷ (180 × 1.001425)) = 27 股，成交金額 4,860，手續費 6。

### P2-03 股利自動帶入
- 依除權息資料，自動為持有中的證券建立股利紀錄（`source = auto`）。
- **參與股數** = 除權息日**前一個交易日**收盤時的持有股數。
- 現金股利 = 參與股數 × 每股現金股利，狀態為 `estimated`；到發放日後改為 `received`。
- 股票股利（配股）股數 = floor(參與股數 × 每股股票股利 ÷ 10)。
- 使用者可修改自動帶入的金額（例如被扣了二代健保補充保費）。修改後該筆不再被自動更新。
- 去重：同證券同除權息日若已有手動紀錄，不自動新增。
- `estimated` 的股利**不計入**總報酬，只在畫面上顯示「預估即將入帳」。

- [ ] 除息日當天才買入的股數，不計入參與股數
- [ ] 已手動輸入的股利不會被重複建立

### P2-04 年化報酬率（XIRR）
- 以現金流計算 XIRR：
  - 買入：`−(成交金額 + 手續費)`，於交易日
  - 賣出：`+(成交金額 − 手續費 − 證交稅)`，於交易日
  - 現金股利（`received`）：`+金額`，於入帳日（無入帳日則用除息日）
  - 期末：`+(市值 − 預估賣出費用)`，於今天
- 計算範圍：單一持股、核心、衛星、整體。
- 演算法：牛頓法，不收斂時改用二分法；仍無解則顯示 `—`。
- 若第一筆現金流距今**不到 365 天**，不顯示年化報酬率，改顯示「持有未滿一年」，避免短期報酬被年化放大而誤導。

**AC**
- [ ] 單元測試：一年前投入 100,000、今天價值 110,000 → XIRR = 10.00%
- [ ] 持有 200 天的持股顯示「持有未滿一年」

- 被鎖住的功能顯示預覽與升級說明，而不是直接隱藏。

### P2-09 買在高點還是低點
**User story**：身為使用者，我想知道我買進的價格，以當時來看是貴還是便宜，才能檢討自己的進場時機。

**比較基準**
- 只用**買入日之前**的收盤價，也就是買的當下看得到的資料。不使用買入後的資料。
- 使用**還原收盤價**，避免除息後股價下跳，讓除息前的買點看起來像買在高點。
- 每筆**買入交易**各自判斷；同一檔股票分批買，每筆都有自己的結果。

**比較區間**（使用者可切換，最長 3 年）

| 選項 | 區間 |
|---|---|
| 3 個月 | 買入日前 3 個月 |
| 6 個月 | 買入日前 6 個月 |
| **1 年（預設）** | 買入日前 1 年 |
| 3 年 | 買入日前 3 年 |
| 自訂 | 使用者選起始日，最早為買入日前 3 年；結束日固定為買入日 |

**判斷方式**
```
百分位 = 區間內「收盤價 < 買入價」的交易日數 ÷ 區間內交易日總數
百分位 ≥ 80%       → 高檔
20% < 百分位 < 80% → 中段
百分位 ≤ 20%       → 低檔
```

**畫面**
- 入口：單一持股頁的每筆買入交易，以及新增買入交易後的結果提示。
- 顯示所選區間的 **K 線圖**（日 K），在買入日標記買入點與買入價。
- 用淺色帶標出高檔區（區間收盤價前 20%）與低檔區（後 20%）。
- 一句話結論，例如「你買在近一年的**高檔**，買入價高於 85% 的交易日」。結論只陳述事實，**不得出現「建議」、「應該」、「買進」、「賣出」等字眼**。
- 切換區間時，K 線、色帶與結論同步更新。

**邊界情況**
- 上市時間短於所選區間：改用上市以來的資料，並註明「上市未滿 1 年，以上市以來 N 個月計算」。
- 區間內交易日少於 20 天：不下結論，只顯示 K 線與「資料不足，無法判斷」。
- 買入價高於區間最高價或低於區間最低價：百分位分別為 100% 或 0%，照常判斷。
- 拍照匯入建立的期初持股，買入日不是真實日期，結論旁註明「買入日為匯入日期，結果僅供參考」。

**依賴**：需要 T15 的歷史價格與還原股價資料，並需要開高低收資料才能畫 K 線；若資料來源只有收盤價，K 線改用折線圖呈現。

**AC**
- [ ] 單元測試：區間內 100 個交易日，有 85 天收盤價低於買入價 → 百分位 85%、高檔
- [ ] 單元測試：百分位剛好 80% 為高檔、剛好 20% 為低檔
- [ ] 自訂起始日早於買入日前 3 年時，不可選取
- [ ] 區間內交易日少於 20 天時，不顯示結論
- [ ] 結論文字不含禁用字眼（單元測試掃描）

### 8.1 P3-09 成交回報 email 自動匯入（詳細規格）

**User story**：身為使用者，我在券商 App 下單成交後，不想再回到這個 App 手動輸入，希望它自動偵測到並問我要不要新增。

**前置條件**：需要 P2-01 帳號（資料存在雲端）與推播通知功能。本功能為 Pro 功能。

#### 整體流程
```
在券商成交 → 券商寄出成交回報 email → 使用者信箱自動轉寄到 App 專屬地址
→ 後端驗證寄件者並解析出交易 → 建立「待確認交易」→ 推播通知
→ 使用者確認（可修改）→ 寫入正式交易
```

#### A. 專屬收件地址
- 每位使用者有一個專屬地址，格式為 `t-{隨機 token}@inbox.{App 網域}`。token 至少 16 個隨機字元，不可由使用者 ID 推算。
- 使用者可「重新產生地址」，舊地址立即失效（地址外洩時使用）。
- 設定頁顯示地址與「複製」按鈕。

#### B. 設定引導
- 提供 Gmail、Outlook、Yahoo 的圖文教學：如何建立「寄件者是券商 → 自動轉寄到專屬地址」的篩選規則。
- **Gmail 轉寄驗證信**：Gmail 新增轉寄地址時，會寄一封含驗證碼的確認信到專屬地址。後端必須辨識這類信件，並把驗證碼或確認連結**顯示在 App 設定頁**，讓使用者完成設定。此類信件不進入交易解析。
- 設定完成後，顯示「等待第一封券商信件」狀態；收到第一封成功解析的信後，改為「已連線：○○證券」。

#### C. 寄件者驗證（防止偽造交易）
- 只處理**支援券商白名單**中的寄件網域（白名單由後端維護，可不改 App 直接更新）。
- 驗證原始寄件網域的 DKIM 簽章（自動轉寄後 SPF 常會失敗，因此以 DKIM 為準）。DKIM 不通過的信件直接捨棄，不通知使用者，但記錄在後端日誌。
- 白名單外的寄件者一律捨棄。

#### D. 解析
- 每家支援的券商有一個**專屬解析器**，依該券商的信件格式擷取欄位。
- 專屬解析器失敗時，可改用 AI 模型解析，要求回傳 JSON，讀不到的欄位為 `null`，**不可猜測**。
- 擷取欄位：證券代號、買／賣、成交日期、成交價、成交股數、委託書號；若信件有手續費、證交稅，一併擷取。
- 同一封信可能包含多筆成交：
  - **同一委託書號的分筆成交合併成一筆**，股數相加，成交價為加權平均。
  - 不同委託書號各自成為一筆。
- 信件中的帳號、姓名、身分證字號等個資**不擷取、不儲存**。
- 原始信件內容在解析完成後**立即刪除**，只保留解析出的交易欄位。

#### E. 待確認交易（PendingTransaction）
新增資料表：

| 欄位 | 說明 |
|---|---|
| `id` | uuid |
| `userId` | |
| `broker` | 券商代碼 |
| `brokerOrderRef` | 委託書號 |
| `symbol`、`side`、`tradeDate`、`price`、`shares` | 同 Transaction |
| `fee`、`tax` | 信件有提供就用信件數字，否則依 3.2 計算 |
| `feeFromEmail` | 手續費與稅是否來自信件 |
| `status` | `pending`／`confirmed`／`dismissed`／`duplicate` |
| `parseMethod` | `template`／`ai` |
| `receivedAt` | 收到信件的時間 |

- 使用者確認後，建立一筆 `source = email` 的正式交易，帶入 `brokerOrderRef`。若手續費來自信件，`feeOverridden = true`。
- 使用者可以忽略，狀態改為 `dismissed`，不再提醒。
- 待確認交易**不計入**任何報酬計算。

#### F. 去重
同一筆成交可能先收到即時成交回報、晚上又收到電子對帳單，必須避免重複：
1. 若已有相同 `broker` + `brokerOrderRef` + `tradeDate` 的交易或待確認交易 → 標記為 `duplicate`，不通知。
2. 信件沒有委託書號時，若已有相同證券、買賣、日期、成交價、股數的交易（任何 source）→ 建立待確認交易，但顯示「可能重複」警告，且**預設不勾選**。
3. 若同一筆先收到成交回報（無手續費）、後收到對帳單（有實際手續費），而前者已確認：不建立新的待確認交易，改為提示「券商對帳單的手續費為 X 元，是否更新？」

#### G. 通知
- 每解析出一批待確認交易，推播一則通知：
  - 1 筆：「偵測到一筆交易：買進 2330 台積電 1,000 股 @ 600」
  - 多筆：「偵測到 3 筆新交易，點擊確認」
- 點擊通知開啟「待確認交易」頁。App 首頁也要顯示待確認數量的提示。
- 收到白名單券商、但無法解析的信件時，通知「收到一封○○證券的信件，但無法辨識內容，請手動新增」。

#### H. 待確認交易頁
- 列出所有 `pending` 項目，每列顯示證券、買賣、日期、價格、股數、手續費、證交稅，**每個欄位都可修改**。
- 支援全選與批次確認。
- 確認時套用 M-02 的驗證規則。賣出股數超過持股時，該列不可確認，並提示「你在 App 內的持股不足，可能是還沒匯入期初持股」，提供前往「拍照匯入」的連結。
- `parseMethod = ai` 的項目標示「AI 辨識，請仔細核對」。

#### 支援券商
- 第一版支援 2–3 家主流券商（名單見待決事項）。
- 收到不支援券商的信件時，在設定頁顯示「目前尚未支援○○證券」，並提供「回報想要支援這家券商」按鈕。

#### AC
- [ ] 從白名單券商轉寄的成交回報，在 1 分鐘內出現在待確認交易並推播
- [ ] 非白名單寄件者、或 DKIM 驗證失敗的信件，不產生任何待確認交易
- [ ] 同一委託書號分 3 筆成交（300、300、400 股），合併為 1 筆 1,000 股，成交價為加權平均
- [ ] 同一筆成交的成交回報與對帳單都轉寄進來，只產生 1 筆待確認交易
- [ ] 待確認交易在使用者確認前，不影響任何持股與報酬數字
- [ ] 確認後產生的交易 `source = email`，在列表上有「email 匯入」標記
- [ ] 原始信件在解析後已刪除，資料庫中查不到信件內文、帳號或姓名
- [ ] 重新產生專屬地址後，寄到舊地址的信件不再被處理
- [ ] Gmail 轉寄驗證信的驗證碼會顯示在 App 設定頁

## 9. 非功能需求

- **正確性優先**：計算引擎的單元測試覆蓋率目標 90% 以上，第 3.7 節與各功能 AC 中的數字範例全部要有測試。
- **效能**：1,000 筆交易以內，首頁總覽在 1 秒內算完。
- **離線可用**：MVP 所有檢視與輸入功能都可在離線時使用。
- **行動裝置優先**：以手機直式畫面為主要設計，寬度 375px 時不可出現水平捲動。
- **隱私**：不蒐集與功能無關的個人資料；截圖不留存；分享卡預設不含金額。
- **無障礙**：盈虧不能只靠紅綠色區分，必須同時有 `+`／`-` 符號。
